# 학부모 계정 및 결제 시스템 계획

플러스 아동발달센터 홈페이지에 학부모 계정과 온라인 결제를 추가하기 위한 계획입니다.

- 작성일: 2026-11-03
- 상태: **개발 보류.** 비용이 필요한 기능은 진행하지 않고, 현재 사이트는 Cloudflare Pages 무료 플랜의 정적 페이지로만 서빙합니다.
- 시연: `feature/toss-payment-demo` 브랜치에서 `npm run dev` 실행 후 `/demo/payment`
- 재개 시 검토: 호스팅 구성은 재개 시점에 다시 결정합니다. Cloudflare 무료 약관 2.2.1(h)의 카드 정보 조항을 먼저 확인해야 합니다.

## 1. 요약

- 관리자가 결제 항목을 추가하면 학부모가 계정에 로그인해 온라인으로 결제합니다.
- 바우처로 결제되지 않는 치료비, 본인부담금, 활동비 등이 대상입니다.
- 바우처는 국민행복카드로 제공기관에서 결제하는 방식으로 안내되어 있어 온라인 결제로 대신하지 않습니다. 단말기 처리 내역은 관리자가 기록합니다.
- 학부모와 아동은 관리자가 만든 연결 코드로 연결합니다.
- 계정과 비용은 센터 명의, 센터 부담입니다.
- 일정은 개발자 1명 기준 약 12~16주로 추정합니다.

## 2. 결정 현황

| 항목 | 내용 | 상태 |
|---|---|---|
| 결제 대상 | 바우처 외 모든 비용 (치료비, 본인부담금, 활동비 등) | 확정 |
| 청구 방식 | 관리자가 항목을 추가하면 학부모가 결제 | 확정 |
| 결제 주기 | 월 단위 (변경 가능성 있음) | 확정 |
| 이용 규모 | 약 100명 추정 | 추정 |
| 계정 대상 | 학부모 (추후 다른 결제자로 확장 가능하게 설계) | 확정 |
| 연결 코드 전달 | 대면, 문자, 링크 모두 지원 | 확정 |
| 비용 부담 | 인프라와 수수료 전액 센터 부담 | 확정 |
| 개발자 역할 | 개발 용역 | 확정 |
| 결제수단 | 카드, 간편결제, 계좌이체, 가상계좌, 휴대폰 결제. 상품권 제외 | 확정 |
| 금액 산정 | 관리자가 직접 입력하는 방식이라 산정 규칙이 없어도 개발 가능 | 미정 |
| 환불 규정 | **4단계 실제 결제 공개 전 확정 필수** | 미정 |
| 월 결제액 | 수수료 추정에 필요 | 미정 |

## 3. 시스템 구성

| 영역 | 선택 | 이유 |
|---|---|---|
| 호스팅 | Vercel Pro | 현재 Next.js 구조 유지, 상업적 사용 가능 |
| 계정·DB | Supabase (서울 리전) | 카카오 로그인 기본 지원, 서울 리전 제공 |
| 결제 | 토스페이먼츠 직접 연동 | 공개 수수료 확인. PG 1곳이면 충분 |
| 알림 | 문자 또는 카카오 알림톡 | 서비스와 비용은 0단계에서 선정 |

저장하지 않을 정보: 카드번호 등 결제 수단 원문, 진단과 치료 기록.

## 4. 기능 설계

### 4-1. 가입과 연결 코드

1. 관리자가 아동을 등록하고 연결 코드를 생성합니다.
2. 코드를 대면(인쇄 또는 구두), 문자, 링크 중 하나로 전달합니다.
3. 학부모가 카카오로 로그인하고 약관과 개인정보 수집에 동의합니다.
4. 휴대폰 인증으로 보호자임을 확인합니다.
5. 코드를 입력하거나 링크로 들어온 뒤, `김*수`처럼 일부 가린 이름을 확인하고 연결합니다.

코드 규칙

- 8자리 이상 무작위, 혼동 문자(0/O, 1/I) 제외
- DB에는 해시만 저장하고 원문은 생성 시 한 번만 표시
- 1회용, 14일 만료, 입력 횟수 제한, 관리자 폐기 가능
- 링크는 코드를 URL 프래그먼트(`/link#코드`)에 담아 서버 로그와 리퍼러에 남지 않게 함
- 링크를 열어도 로그인, 동의, 인증을 거쳐야 연결됨

연결 구조: 아동 1명에 결제자 여러 명, 결제자 1명에 아동 여러 명(형제자매)을 허용합니다. 잘못 연결되면 관리자가 해제하고 코드를 재발급합니다.

### 4-2. 결제 항목

- 관리자가 아동, 구분, 항목명, 금액, 납부 기한을 입력합니다.
- 금액 산정 규칙이 정해지면 자동 계산을 추가합니다.
- 월 단위 일괄 입력을 지원합니다: 지난달 복사 또는 CSV 업로드 후 관리자 확인.
- **관리자가 확인한 뒤에만 발송합니다.** 금액 오류가 전체에 한 번에 나가는 것을 막기 위해서입니다.
- 주기 변경에 대비해 월 대신 청구 시작일과 종료일을 저장합니다.
- 자동결제는 첫 버전에서 제외합니다.

### 4-3. 결제

1. 학부모가 항목을 하나 이상 선택합니다.
2. 서버가 항목과 소유 관계를 확인하고 주문을 만듭니다.
3. PG 결제창에서 결제합니다.
4. 서버가 **DB 금액과 대조한 뒤** 승인합니다. 브라우저가 보낸 금액은 믿지 않습니다.
5. 웹훅으로 상태를 맞추고, 반복 요청이 들어와도 이중 결제되지 않게 합니다.
6. 가상계좌는 입금 웹훅을 받아야 완료 처리합니다.

### 4-4. 관리자

- 아동 등록, 연결 코드 발급과 폐기, 항목 관리, 미납 목록과 재안내
- 단말기·바우처 결제의 수기 기록
- 환불 처리와 결제 내역 내보내기
- 모든 조회와 변경을 기록

## 5. 데이터 구조

| 테이블 | 내용 |
|---|---|
| `profiles` | 사용자, 권한(학부모, 직원, 관리자) |
| `children` | 아동 이름, 생년월일 |
| `link_codes` | 코드 해시, 대상 아동, 전달 방식, 만료, 사용 여부 |
| `payer_links` | 결제자와 아동의 연결, 관계 유형 |
| `consents` | 동의 항목, 약관 버전, 시각 |
| `charges` | 아동, 구분, 항목명, 금액, 기한, 청구 기간, 상태 |
| `orders`, `order_charges` | 주문과 포함 항목 |
| `payments` | 결제사 거래 번호, 수단, 상태 |
| `refunds` | 환불 금액, 사유, 처리자 |
| `offline_settlements` | 단말기·바우처 수기 기록 |
| `notifications` | 발송 내역 |
| `audit_logs` | 직원의 조회·변경 기록 |

## 6. 보안

- 모든 테이블에 행 단위 접근 제어(RLS)를 적용하고, 타인 아동 접근 차단을 자동 테스트합니다.
- 비밀 키와 서비스 권한 키는 서버에만 둡니다.
- 직원 계정은 2단계 인증을 사용합니다.
- 웹훅 진위를 검증합니다.
- 접속 기록과 백업을 운영합니다.
- 개발과 테스트에는 실제 아동 정보를 쓰지 않습니다.

## 8. 소유와 계약

- Vercel, Supabase, 도메인, 카카오 개발자, 알림 서비스는 센터 소유로 만들고 개발자는 멤버로 참여합니다.
- 토스페이먼츠 가맹점과 정산 계좌는 센터 사업자 명의입니다.
- 개인정보 처리자는 센터이며, 개발자는 수탁자에 해당할 수 있습니다.

계약서 검토 항목

- 개인정보 처리 위탁 내용과 운영 데이터 접근 범위
- 저작권은 제작자에게 있으므로 센터의 사용 범위, 계약 종료 후 사용 조건
- 인수 후 장애 대응 범위, 결제 오류 시 책임, 추가 개발 비용

## 9. 법률 검토 항목

법령 원문과 관할 기관, 전문가 확인이 필요합니다.

- 만 14세 미만 아동 정보: 법정대리인 동의와 그 확인 (개인정보 보호법 제22조의2)
- 관리자가 먼저 등록하는 아동 정보의 수집 근거와 동의 시점
- 치료 관련 정보의 민감정보 해당 여부
- 통신판매업 신고 대상 여부. 면제 기준이 자료마다 다릅니다.
- 사업자 정보와 환불 조건 표시, 청약철회 시 환급 기한
- 치료 서비스에 적용되는 환불 기준 (아직 찾지 못함)
- 처리 위탁과 국외 이전 여부를 개인정보처리방침에 반영
- 현금영수증 등 세무 처리

## 10. 일정

개발자 1명 기준의 대략적인 추정입니다. PG 심사 기간은 확인하지 못했습니다.

| 단계 | 내용 | 완료 기준 | 기간 |
|---|---|---|---|
| 0. 계약·확인 | 결정 필요 항목, 계약, 센터 명의 계정, 법률 검토 | 계정 준비, 요율 확인 | 1~2주 |
| 1. 기반 | Vercel 이전, Supabase, 상담 폼 저장·알림 | 실제 신청이 직원에게 도착 | 약 1주 |
| 2. 계정 | 로그인, 동의, 연결 코드, 관리자 | 코드 악용과 타인 정보 접근 테스트 통과 | 2~3주 |
| 3. 청구 | 항목 관리, 일괄 입력, 발송, 수기 기록 | 한 달치를 기존 장부와 비교해 일치 | 2~3주 |
| 4. 결제 | PG 심사, 결제, 웹훅, 환불 | 테스트 환경에서 성공·실패·중복·환불 통과 | 2~3주 |
| 5. 시범 운영 | 보안 점검, 5~10가정 실제 사용 | 한 달 정산 일치 후 전체 확대 | 약 4주 |

4단계 공개 전 환불 규정이 확정되어야 합니다.

## 11. 시연 범위

`/demo/payment`에서 확인할 수 있습니다.

| 시연되는 것 | 시연되지 않는 것 |
|---|---|
| 관리자 항목 추가와 삭제 | 로그인, 연결 코드 |
| 학부모 항목 선택과 합계 | 실제 PG 연동과 정산 |
| 결제수단 선택, 완료, 실패 | 카드 정보 입력 |
| 가상계좌 발급과 입금 확인 | 환불, 알림 발송 |
| 결제 내역 | 서버 저장, 기기 간 공유 |

시연 데이터는 해당 브라우저에만 저장됩니다. 실제 결제 연동 시 `app/demo`, `app/api/demo`, `components/payment-demo`, `lib/payment-demo`와 `@tosspayments/tosspayments-sdk` 사용 코드를 정리합니다.

### 토스 테스트 연동

`.env.local`에 `test_`로 시작하는 키를 넣으면 토스 테스트 결제가 켜지고, 키가 없으면 모의 결제창으로 동작합니다. 실제로 돈이 결제되지 않으며, 라이브 키는 코드에서 거부합니다.

| 변수 | 내용 |
|---|---|
| `NEXT_PUBLIC_TOSS_CLIENT_KEY` | 테스트 클라이언트 키 (`test_gck_` 주문서형, `test_ck_` 결제창) |
| `TOSS_SECRET_KEY` | 같은 세트의 테스트 시크릿 키. 서버에서만 사용 |

금액은 시연 데이터가 브라우저에 있어 브라우저 값을 서명 쿠키로 보관해 대조합니다. **실제 서비스에서는 DB의 청구 금액으로 주문을 만들어야 합니다.**
